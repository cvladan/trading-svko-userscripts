# SVKO TradingView Alert Speech

Version `0.2.1` speaks only new TradingView alert toasts containing `[say]` or `[say:language]`, generates speech through OpenRouter and saves audio recordings in this userscript's Tampermonkey storage. Repeated messages reuse their saved recording. The panel shows the last message, time, count and speech status.

## Use

The script starts automatically on `https://www.tradingview.com/chart/*`. To turn it off, disable the userscript in Tampermonkey and reload the chart. There are no Start or Stop menu commands.

Choose **Speech settings** from this script's Tampermonkey menu. Enter your OpenRouter API key, model slug and default language. Expand Request JSON to edit voice, audio format and provider options. All three sections can be collapsed. Speech starts open; Request JSON and Test speech start closed whenever the dialog opens. Defaults are `google/gemini-3.8-flash-tts`, Kore and `en`. The saved key is loaded into the field; the **Show** and **Hide** control inside the field toggles its visibility. A blank field preserves the saved key. The dialog uses dark fields and buttons with visible keyboard focus. Its height follows the visible content when sections open or close, capped at 90% of the viewport with scrolling for longer content. The form uses its own iframe document so TradingView keyboard shortcuts do not intercept typing or paste. Save applies the settings and restarts detection automatically. The dialog separates speech settings, request JSON and testing. **Test speech** uses the current fields and test message without saving settings, then restores the saved configuration. The test restarts the listening session, clearing its count and queue. It saves successful recordings and reports whether a recording was generated or reused. Save remains a separate action.

Existing toasts are treated as already seen. New alerts update the panel and speak in order, without overlapping. If the browser blocks automatic playback, click **Enable audio** in the panel; queued alerts wait for this gesture. Without a saved API key, detection still works but messages are not queued for later speech.

Each matching tab runs independently. There is no coordination between tabs, so multiple chart tabs may speak the same alert and simultaneous initial generation may duplicate requests. Reloading or saving settings resets the count and clears waiting alerts. Completed recordings remain saved. Aborting a request cannot guarantee that the provider has not already charged for generation.

The relevant alerts must have TradingView's toast notification enabled. This script reads the page's alert list, not operating system notifications or alert history. Other notification groups, including order notifications, are ignored. Native alert sounds and toast controls are unchanged. Turn off the native sound in the relevant TradingView alerts if you want speech alone.

## Language tags

Put `[say]` anywhere in the message to use the saved default language. Use `[say:sr]`, `[say:en]` or another BCP 47 code for an explicit language. Both forms are removed from the spoken text. For example, `Price [say:en] crossed the level.` and `[say:en] Price crossed the level.` produce the same spoken text. Tag names are case insensitive. Repeated identical language tags are allowed; conflicting languages, empty codes and invalid codes pause speech with an explanation.

Only alerts with a `[say]` or `[say:language]` tag enter the speech queue. Without one, there is no recording lookup, generation or playback, even if an older recording exists. `[sound:name]` alone belongs to Custom Sounds and never triggers Speech. When both tags are present, the scripts act independently and both speech and sound tags are removed from the spoken text. Remaining whitespace is collapsed and the text is trimmed. The explicit Test speech button can still preview untagged text using the saved default language. Tags guide pronunciation and do not translate text. Write the message in the language you want to hear. Model language support and actual pronunciation still depend on the provider; accepting a syntactically valid language code does not guarantee model support.

## Speech and saved recordings

The default model is `google/gemini-3.8-flash-tts`, verified in the OpenRouter catalogue on 2026-10-02. Requests use the [OpenRouter speech endpoint](https://openrouter.ai/docs/guides/overview/multimodal/tts), `POST https://openrouter.ai/api/v1/audio/speech`.

**Request parameters** is the editable JSON object for all request fields except `model` and `input`. Those two fields always come from the model setting and the cleaned alert or test message. Including either in the parameters object is an error. JSON must be an object, not an array, string or null. Invalid JSON prevents both saving and testing. Parameters are parsed as data, never executed.

Set `voice`, `response_format`, `provider`, delivery instructions and any other model options directly in this JSON. Parameters are sent as entered after placeholder substitution. A custom JSON object is not merged with hidden Google defaults. Choosing another model preserves the JSON, so remove or change provider options that do not apply. **Load model defaults** explicitly replaces the editor contents: Google defaults use Kore, PCM and Google AI Studio; other models start with `{"response_format":"mp3"}` and may require a voice or additional options. Loading defaults does not save settings.

Two placeholders work anywhere inside JSON string values, including nested objects and arrays. `{{language}}` expands to the canonical alert language, such as `sr`, `en` or `en-GB`. `{{locale}}` expands a bare code to its likely region, such as `sr-RS` or `en-US`, while preserving explicit regional tags. Substitution happens after parsing, so quotes and line breaks remain valid JSON. Object keys are not substituted. Without either placeholder, language tags do not alter the manually specified parameters.

**Request preview** shows the exact complete body for the current test message, with `model`, `input` and resolved placeholders. It updates when the model, language, parameters or test message changes. The API key is sent separately as the Authorization header. **Test speech** sends this same request, or reuses its saved recording, without saving the form's settings.

The Google default template selects `google-ai-studio` and passes `speechConfig: { voiceConfig: { voice }, languageCode: "{{locale}}" }` under `provider.options['google-ai-studio']`. This follows Google's [GenerateContent SpeechConfig schema](https://ai.google.dev/api/generate-content#SpeechConfig), not the Interactions API array. Other models need the options their provider supports; no top-level language parameter is added automatically.

Playback uses signed 16 bit little endian mono PCM at 24 kHz when `response_format` is `pcm` or omitted. Other requested formats use the browser's audio decoder and require an audio content type. The selected model must support the requested format, and the browser must be able to decode it. Arbitrary request options do not imply support for every provider or audio encoding.

Existing settings without a JSON template are converted into equivalent parameters using the previously saved model, voice and format. Opening the dialog does not write settings. Save stores the edited object as `requestParameters`. Existing recordings remain available when the resolved request is unchanged.

The default Google model rejected MP3 with a specific HTTP 400 message. It also rejected the Interactions `speech_config` array with a generic provider 400. Live English and Serbian requests succeeded with PCM and GenerateContent `speechConfig` on 2026-10-02. Model support for other languages still depends on the provider.

Settings use `svko-alert-speech:settings`. Recordings use `svko-alert-speech:audio:v1:` followed by a SHA-256 digest of the language and complete generation request. The identity includes the cleaned text, model, voice, format and language delivery options; toast time and tag position do not affect it. Each record contains the request and Base64 encoded audio bytes. The API key is stored only in settings, not in recording records, source code or logs.

Each queued event checks storage before generating. A new response must have a successful HTTP status, the requested audio content type, at most 10 MiB of audio and pass browser audio decoding or PCM conversion before storage. It is saved before playback. A storage, API, decoding or playback error pauses speech and clears waiting alerts, while detection continues. There are no automatic retries or fallback voices. After correcting the problem, reload the chart or save settings again; previous toasts are not replayed. A corrupt saved recording causes an error rather than silently generating a paid replacement. This version has no recording management UI.

Requests have a 60 second network timeout. A maximum of 100 waiting alerts prevents unbounded queue growth; exceeding it clears the waiting queue and pauses speech with a visible message. Reloading and errors do not delete saved recordings. There is no automatic recording expiry or eviction in the script. Storage remains subject to browser and extension limits and user deletion, and is not a backup. Changed prices in message text create different recordings.

Only one recording is generated, decoded and played at a time. Audio uses one AudioContext per active audio session, closed when the session ends. Playback is attempted automatically; a direct page click enables audio when required by browser restrictions. Background playback has not yet been verified.

During development, settings and recordings belong to **SVKO Dev**. A separate production entry has separate Tampermonkey storage. Do not discard the development archive or promise automatic transfer when publishing; migration must be handled explicitly before ending development if recordings should be retained.

## Detection and resource limits

The script finds `[data-name="toast-group-expand-button-alerts"]`, resolves its `aria-controls` value and observes only the containing `role="log"` element. It does not hardcode generated IDs or complete CSS class names. Message and time come from descendants with the `description-` and `time-` class prefixes.

There is one observer instance, reused when settings restart the session. During asynchronous chart startup it temporarily watches child changes under `body` until the alert container becomes available, then disconnects and observes only that log. There are no polling loops or periodic timers. The host, protocol, chart path and top frame are checked before startup. Only the Speech settings menu command is registered. Recordings are accessed only for queued speech.

A toast is ready when both message and time are nonempty. A WeakMap remembers its last message and time, so unchanged rerenders do not count again. A new toast element counts even when its message matches an earlier event. A changed message or time in a reused element also counts. Incomplete toasts already present at startup are ignored when first completed. The panel is outside the observed container and displays content using text setters.

This is DOM detection, not access to TradingView event IDs. Recreating an old toast as a new DOM element can count it again. Two events that reuse one element with exactly the same message and displayed time cannot be distinguished. If TradingView replaces the entire observed log, reload the chart or save settings again to attach to the new container. No background watchdog is added for this trial.

## Development and validation

Follow [AGENTS.md](AGENTS.md), [SVKO Dev.md](SVKO%20Dev.md) and [PUBLISH.md](PUBLISH.md). Use the single universal development slot, preserving its metadata and storage. Production grants are `GM_registerMenuCommand`, `GM.getValue`, `GM.setValue` and `GM_xmlhttpRequest`, with `@connect openrouter.ai`. It runs at `document-idle` in the top frame of the chart URL above. Do not run development and production copies together. The universal loader already has these grants and does not need changing.

Keep this guide synchronised with behaviour, permissions and installation status. Preserve the one observer limit, narrow observation scope after startup and automatic activation. Never put credentials or real user audio into repository files or tests. Preserve the original comments. Display the complete response body for failed API requests as text, including nested provider details. Redact the configured API key if echoed. Do not replace HTTP 400 with an unsupported claim about insufficient credits. Empty error bodies retain a clear status message.

Run `node --check 'SVKO TradingView Alert Speech.user.js'`. The DOM tests use jsdom 26.1.0 outside the repository. Install it with `npm install --prefix /tmp/svko-alert-validation --cache /tmp/svko-alert-validation/npm-cache --no-audit --no-fund --ignore-scripts jsdom@26.1.0`, then run `NODE_PATH=/tmp/svko-alert-validation/node_modules node 'SVKO TradingView Alert Speech.test.cjs'`. Pass `SVKO Dev.user.js` as the final argument to check the development source instead.

The 15 scenarios cover automatic startup, existing and incomplete baseline toasts, new and delayed messages, identical events in distinct nodes, unchanged content, reused nodes, character data updates, unrelated notifications, repeated Start, Stop, restart, literal text rendering, missing and replaced containers, and protocol, host, path and frame guards. Syntax checks and synthetic DOM tests do not establish live TradingView detection.

Also run `NODE_PATH=/tmp/svko-alert-validation/node_modules node 'SVKO TradingView Alert Speech.speech.test.cjs'`, optionally with `SVKO Dev.user.js` as the last argument. Its 22 scenarios use synthetic credentials, responses and audio only. They cover ignoring untagged and sound-only alerts before audio or storage access, suppressing cached speech after removing the speech tag, cleaning combined tags, activation, tags anywhere, sequential playback, saved reuse across page sessions, default language, changed voice, invalid tags, cancellation, storage/API/audio failures, invalid responses and custom model requests, settings persistence, saved-key visibility toggling, PCM sample conversion, full error responses, unsaved test settings, manual format selection and restoring saved preferences after tests, arbitrary JSON options, language placeholders, protected model and input fields, live preview and explicit default loading.
